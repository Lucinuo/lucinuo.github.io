# Lucinuo 網站上線前檢查

每次準備合併網站變更或部署前，以及 Lucille 說「跑上線前檢查」時，執行這份清單。檢查待合併或待部署版本，並以 [公開網站](https://lucinuo.github.io/) 為基準。每次回報註明檢查的是哪個版本及網址。檢查過程唯讀。公開網站、原始碼與報告都應守住 SJF 私有內容及私人工作區的邊界。

## 開工

1. 若在 Lucille 的 Claude 工作區接手，先讀交班摘要（LIVE）和協作協議。接著查上一次上線前檢查的紀錄與 Lucille 已定案的例外。找不到前次紀錄就標明。
2. 在網站 repo 執行 `git fetch origin`，核對本機、GitHub 的 `origin/main` 和線上部署版本。若 iCloud 管理的檔案讀取逾時或 fetch 失敗，記下錯誤，改用 GitHub API 比較本機 commit 與遠端 `main`。本機原始碼讀不到時，可檢查線上檔案，並標明待發布版本有哪些部分仍無法核對。
3. 在**網站 repo 根目錄**執行 `node tests/site-validation.test.cjs`，記錄結束碼。測試通過只代表它涵蓋的項目通過。其餘項目依下節用真實瀏覽器核對。

## 瀏覽器實測

用真實瀏覽器開啟待上線版本的預覽，檢查桌機（1440 × 900）與手機（375 × 812）。兩種尺寸都切換中文、英文、深色及淺色。若只能開啟公開版，回報中標明待上線版本尚未實測。

- 查看首頁第一印象、導覽與頁內跳轉、Research／Publications／Projects／About 的主要流程，以及手機選單能否開關。
- 檢查主要按鈕及連結的觸控區至少 44 px 高，手機頁面沒有水平溢出。
- 用鍵盤走過 Tab 順序，確認焦點清楚可見、被遮住的元素不會取得焦點，並用 Enter 和空白鍵測試按鈕。
- 檢查一般文字對比至少 4.5:1（大字除外），圖片有替代文字且正常載入，媒體預設不自行出聲。
- 逐一檢查站內連結，列出壞連結與載入感受。測試時自行輸入的不存在網址（例如 `/research/`）所回傳的 404 不計入。
- 切換尺寸後等畫面穩定再點。模擬按鍵或點擊無反應時，先查程式有無對應處理。仍無法判斷時記「待 Lucille 實機確認」。

## 精選工作

**這裡是首頁精選卡規格的唯一正本。換卡時，在改網站的同一筆 commit 更新本節，並同步 `tests/site-validation.test.cjs` 的精選卡驗證。** 2026-11-14 在公開首頁確認的順序如下。

1. Ink Current（近期實驗，`/ink-current/`）
2. Phase Shift（成熟代表作，`/projects/phase-shift/`）
3. Lucinuo Website System（成熟代表作，`/projects/#lucinuo-site`）

- 讀出首頁實際顯示的三張卡與順序，並核對每張都對應 `/projects/` 上的作品與連結。首頁與規格不符時列為「中」，並列出兩邊的內容，交 Lucille 決定改網站或改規格。
- 近期實驗沒有固定輪替。新作品須能完整體驗核心流程，且更能代表目前的探索方向，才建議替換。成熟代表作的替換須已公開、主要流程完整、桌機和手機皆穩定，並展現明顯更強的新能力。
- Urolithin A 動畫頁屬於 Research，不占精選卡。Growth Compass 維持封存。Bearing 維持現有公開概念與私人資料的邊界。

## 嚴重度

- **高**：主要流程壞掉、隱私外洩或整頁無法開啟。
- **中**：和規格不一致，或主要功能在其中一種裝置上不能用。
- **低**：體驗瑕疵。

完成檢查且沒有高、中問題即為「通過」。關鍵檢查無法完成時，回報尚未確認的項目。

## 回報給 Lucille

1. 白話先說本次是否通過，附版本、網址與測試結束碼。
2. 問題表欄位為「嚴重度｜問題｜重現方式（網址、裝置、步驟）｜建議優先順序」。
3. 精選卡逐張寫明維持或更換建議。更換建議要附符合門檻的理由。
4. 前次已報且仍存在的問題標「前次已報」。Lucille 已定案保留的行為不再列為問題。
5. 將結論保留在這次的合併請求或部署紀錄，方便下次接續查驗。
